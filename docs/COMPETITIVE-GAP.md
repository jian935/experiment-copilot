# 对标：旗舰实验平台有什么，我们缺什么

> 版本：2026-11-02 ｜ 对标对象：GrowthBook、Eppo（现 Datadog Experiments）、Statsig、Optimizely
> 信息来自各家公开文档/定价页（2026-11），不是对某个具体版本的评测。

## 一、先把「可比的部分」划出来

把「实验平台」当成一个东西来比，会得出「我们缺 SDK、缺权限、缺 bandit」这种结论——
但那不是缺陷，那是**定位不同**。三类能力必须拆开看：

| 层 | 内容 | 旗舰怎么做 | 我们 |
|---|---|---|---|
| **A. 交付层** | 分流 SDK、feature flag、实时事件管道、灰度发布 | 核心资产，24+ 语言 SDK，边缘节点求值 | **不做**。我们假设「数据已经躺在表里」 |
| **B. 分析层** | 统计引擎、方差削减、护栏、多重比较、序贯 | 各家都在砸钱的地方 | **做了，而且深度不差** |
| **C. 决策层** | 把统计结果翻译成「上不上」，并留下痕迹 | 部分有（decision framework / scorecard） | **做了，且做得比旗舰更「说人话」** |

所以下面这张表主要比 B 和 C。A 层的空缺是**有意的边界**：做半个 SDK 出来，既打不过 GrowthBook 的 24 个 SDK，
也会把「拿到数据之后」这件事做浅。

**M16 的例外**：A 层里真正和「结论可信」直接相关的四件事——权限、审批、审计、API——后来用一个**零依赖可选后端**
补上了（见 `npm run server`）。理由不是「旗舰有所以要有」，而是：**前端的权限是假的**，
而假权限比没有权限更危险。分流 SDK 与 feature flag 仍然不做。

## 三、真正该补的（按对「AI 产品经理」岗位的说服力排序）

不是按「旗舰有就补」，而是按**它能不能证明我理解实验这件事的完整生命周期**：

| 优先级 | 缺口 | 为什么值得补 | 状态 |
|---|---|---|---|
| **P0** | **实验前：样本量与可检出效应** | 旗舰都有，而我们只有事后的「还要跑几天」。PM 上岗第一个问题就是「这个实验要跑多久 / 我的流量够不够」。答不上来，实验就会在第 3 天被「看起来有效果」叫停 | ✅ 本轮补（`#/plan`） |
| **P0** | **决策留痕** | 旗舰叫 decision framework / scorecard。它的价值不是记流水账，而是「三个月后有人问为什么上，能翻出当时的依据与口径」 | ✅ 本轮补（`#/decisions`） |
| **P0** | **让 AI 也能算样本量** | 这是本项目最独特的地方：AI 不参与数字，但它**能调用引擎**去算。旗舰的 AI 助手给的是话术，我们的 AI 给的是可复算的数 | ✅ 本轮补（工具 `plan_experiment`） |
| P1 | 去极值（winsorize） | ARPU 长尾会让方差被几十个极端用户主导。做起来不复杂（截尾 + 敏感性对照），但必须同时给出「截尾前后结论是否翻转」 | ✅ 本轮补：五档截尾扫描 + 收入集中度 + 单点杠杆（精确 leave-one-row-out）。模拟反过来说明「截尾更显著」是换假设换来的（检出率 3.67%→68.67%，覆盖率 94.67%→33.67%），所以它只做诊断、不进决策；粒度实验（54.9%/12.9%/3.0%）把「只能当整格用」写进了界面 |
| P1 | 多臂（A/B/n） | 需要数据结构（variant 不止两个）+ 统计（Dunnett 或 α 分摊）+ UI 全链路改造，属于「大改」 | ✅ 本轮补：统计层用 Dunnett（全零族误报率 5.34%/5.04%，naive 9.41%/12.75%）、决策口径、`#/plan` 3/4 臂、导入层任意臂名 + 误判防线、详情页多臂面板 |
| P1 | 任意维度切片 | 现在固定 device × tenure。真实分析常按渠道/城市/版本切，但数据里没有这些字段——**要先解决导入层的多维度支持** | 待做 |
| P2 | 指标字典可编辑 | 纯前端可以做（本地版本化），但价值低于前几项：口径字典现在已经是「唯一真源」，只是不能改 | 待做 |
| — | 后分层 / Holdout / CUPED++ | 学术价值高于 PM 岗位价值；且后两者需要跨实验的长期数据，导入的数据形态撑不住 | 不做 |

## 四、我们不该跟着做的东西（以及为什么）

这部分比「补了什么」更能说明产品判断：

1. **SDK / feature flag / 分流**。GrowthBook 有 24+ SDK、边缘求值、粘性分桶。我们做不了，也不该做：
   目标用户是「手里已经有实验结果数据的产品/数据同学」，不是「要接 SDK 的客户端工程师」。
   做半个 SDK 只会让人问「那你分流准不准」——而这个问题的答案永远比不上专业平台。
2. **权限 / 审批 / 审计：做了（但只做真的那部分）**。当时写的理由是「纯前端没有后端，权限只能是 UI 上藏起来」——
   这个理由本身没变，变的是**我们补上了后端**。所以现在是真密码、真会话、真角色、真审计；
   仍然不做的是 **SSO**：没有 IdP 可对接，做一个假的 SSO 登录页就回到了「装」的老路。
3. **Bandit / 自动调流**。它优化的是「跑实验期间的收益」，代价是「牺牲统计可解释性」。
   我们的全部价值建立在「每个数字都能复算」上，自动调流会直接破坏这个前提。
4. **实时事件管道**。没有后端就不可能有实时。我们的形态是「导入一份数据，得出可复算的结论」，
   实时监控属于另一套架构。

## 五、反过来：旗舰没有而我们有的一件事

**幻觉数字率 0.00% 的自动评测。**

旗舰的 AI 助手（GrowthBook 的 AI Analyst、Eppo 的自然语言查询）给的是**建议与查询**，
数字由 SQL/引擎产出，所以它们不需要回答「模型会不会编数」这个问题。

而我们的 Agent 会直接用自然语言答数字（「这个实验提升了 1.32pp」）。这带来一个旗舰不需要面对的
风险：**模型可能说一个引擎里不存在的数**。所以我们必须自证：

- 每个数字都要求能在工具输出里找到出处，可疑数字率 **0.00%**（2200 条问答 / 13546 个数字）；
- 引用覆盖率 100%（分母只算「有证据可引」的 1840 条）；
- 口径陷阱 100%（80 条）、路由 100%（1560 条）、工具覆盖 16/16。

这不是「我们也做了评测」，而是**产品形态决定了我们必须多一道自证**。这条在面试里比
「我们也支持 CUPED」有信息量得多——它说明我知道「引入 LLM 之后，哪些保证会失效」。

## 六、结论

- B 层（统计）基本对齐。明确还落后的只剩三项：**CUPED++的多协变量**、**任意维度切片**（要先让导入层支持多维）、
  **指标字典可编辑**（P2）。多臂与去极值已补齐——
  而且去极值这一项我们比旗舰多说了一句话：**截尾后的 p 不能当显著性结论**（区间覆盖真值仅 33.67%，名义 95%），
  所以它进的是诊断面板，不是决策口径。
- C 层（决策）原本只有「结论」，缺「事前规划」与「事后留痕」——**这两块是本轮补的**，补完才闭环：
  `设计 → 运行 → 分析 → 决定 → 留痕`。
- A 层（交付）里与「结论可信」相关的权限/审批/审计/API 已用可选后端补齐；分流 SDK、feature flag、
  实时事件管道仍然不做，边界写在 README 里，避免被当成「不完整的实验平台」。
